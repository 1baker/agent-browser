# Observability Dashboard

Monitor agent-browser sessions in real time with a local web dashboard showing a live browser viewport and command activity feed.

## Usage

The dashboard is bundled into the binary and requires no separate install. Start the server and open any session:

```bash
agent-browser dashboard start
agent-browser open example.com
```

Then open `http://localhost:4848` in your browser to see the live dashboard.

All sessions automatically stream to the dashboard. No extra flags are needed.

## Dashboard login

The dashboard protects its operator APIs with an app-owned login screen. On
first start it creates `~/.agent-browser/dashboard-auth.json` with hashed
superuser credentials and writes bootstrap credentials to the mode-0600 file
`~/.agent-browser/dashboard-auth.env`.

The default `admin` account is a superuser. A `codex` observer is also created
for agent observation through trusted ingress. The dashboard records
`AGENT_BROWSER_DASHBOARD_AUTH_FILE` in `~/.agent-browser/.env` so foreground
runs and the user-scoped service use the same auth store.

For passwordless phone access over a private tailnet, keep the dashboard bound
to localhost and expose it only through Tailscale Serve. Set
<code>AGENT_BROWSER_DASHBOARD_TAILSCALE_AUTH=1</code> and put the exact operator
login in <code>AGENT_BROWSER_DASHBOARD_TAILSCALE_ALLOWED_LOGINS</code>. The
allowlist accepts comma-separated logins. Tailscale identity is accepted only
for HTTPS requests whose forwarded host ends in <code>.ts.net</code> and whose
<code>Tailscale-User-Login</code> header matches the allowlist. Do not enable
this mode when Funnel, Cloudflare, or another reverse proxy can reach the same
listener.

That authenticated dashboard origin also proxies <code>/guacamole/*</code> to
the loopback-only Guacamole service. The proxy removes caller identity headers
and dashboard cookies, then supplies the configured
<code>AGENT_BROWSER_GUACAMOLE_HEADER_USER</code> only after dashboard
authentication. Configure
<code>AGENT_BROWSER_REMOTE_VIEW_EXTERNAL_URL</code> as the private
<code>https://&lt;node&gt;.&lt;tailnet&gt;.ts.net/guacamole/</code> base so
durable <code>/remote-view/&lt;handoff-id&gt;</code> links and provider routes
share one authenticated phone-accessible origin. Keep port 8092 on loopback.

### Custom stream port

By default each session binds its WebSocket stream server to an OS-assigned port. To use a specific port, set the `AGENT_BROWSER_STREAM_PORT` environment variable:

```bash
AGENT_BROWSER_STREAM_PORT=9223 agent-browser open example.com
```

You can also use the runtime commands to control streaming on a running session:

```bash
agent-browser stream enable --port 9223
agent-browser stream status
agent-browser stream disable
```

## Dashboard features

The dashboard is an operations console with routeable operator areas:

Dashboard sections are URL-addressable. Use <code>/service</code> for the
Service view, <code>/browsers</code> for Browser sessions, and
<code>/activity</code> for the activity stream. The Service view preserves its
active record workspace in <code>?view=service:&lt;name&gt;</code> with values
such as <code>service:browsers</code>, <code>service:profiles</code>,
<code>service:incidents</code>, <code>service:sessions</code>,
<code>service:tabs</code>, <code>service:jobs</code>, and
<code>service:events</code>. The left workspace navigator separately persists
the selected workspace, browser, session, tab, profile, and job query
parameters so refreshes and handoff links reopen the same operational view.

## Local Runtime Publish

Dashboard source changes are not visible on the long-running local dashboard
service until the dashboard export is embedded into the installed CLI and the
user service is restarted. For operator-visible QA on
<code>http://127.0.0.1:4848</code>, run:

```bash
pnpm publish:local-dashboard -- --expect-marker "Stream port"
```

When one retained browser must survive publication, add
<code>--expect-retained-session</code>,
<code>--expect-retained-profile</code>,
<code>--expect-retained-target</code>, and
<code>--expect-retained-url</code>. The publisher reads that exact daemon and
CDP target before backup or quiescence, pins its PID and DevTools endpoint, and
requires the same identity after handoff and at final readiness. Missing,
ambiguous, or changed evidence stops the operation. The pinned identity is
also journaled so recovery cannot publish readiness around a lost target.
Use <code>pnpm check:local-dashboard-retained-browser --</code> with the same
identity flags for a read-only preflight that does not lock, build, or launch a
replacement daemon or browser.

After the operator selects the intended page in a retained browser, the pin
operation can instead take only
<code>--discover-retained-url-prefix https://chatgpt.com/g/WORKSHOP_PROJECT_ID/</code>.
It reads current daemon and CDP inventories without navigation or launch and
requires exactly one ready page target beneath the reviewed origin and path.
Zero or multiple matches, degraded browser health, incomplete identity, an
unreadable live lane, and origin or path-prefix drift fail before either private
authority file is written. The durable requirement records the discovered
target's exact URL and stable identity, never the broader prefix.

To remove the manual navigation handoff, run
<code>agent-browser install workstation prepare-retained-browser --url EXACT_URL --url-prefix REVIEWED_PROJECT_PREFIX --runtime-profile PROFILE --json</code>.
The command uses only route-bound <code>remote-view open</code>, verifies exact
rendered URL, profile, target, browser, session, and operator-visible route
agreement, then requires one exact-URL and exact-profile discovery match before
pinning. Its daemon session is the runtime-profile id, so an ambient default
lane cannot satisfy preparation. It has no page interaction or prompt-submission action.
The preparation controller is included in the versioned source-free workstation
support payload and does not require the repository checkout.

The command builds <code>packages/dashboard/out</code>, rebuilds the local CLI,
backs up and replaces <code>~/.local/bin/agent-browser</code>, restarts
<code>agent-browser-dashboard.service</code>, and verifies the live dashboard
URL. Without a user systemd bus, the publisher validates the standalone
dashboard PID, owner, command, and dashboard-mode evidence before signaling
that exact listener. Identity mismatch fails closed. Required readiness checks
read the served HTML, requested bundle markers,
and <code>/api/runtime/manifest</code>, then verify the package version, service
UI contract, embedded dashboard SHA-256, supported UI features, current
executable path, and current executable SHA-256. The publish command fails when
those checks do not match the installed binary it just wrote.

Rendered-page QA then uses a disposable browser. A known failure to launch that
browser before renderer acquisition is returned separately as
<code>browser_launch_unavailable</code> and does not invalidate proven HTTP
readiness. Authentication, DOM, workspace, and other post-launch failures stay
fatal. Add <code>--require-browser-smoke</code> when disposable-browser launch
must be a required gate, or <code>--skip-browser</code> for an HTTP-only publish.
The smoke reads the installed launch capability and uses patched Chromium only
when its manifest, executable, artifact smoke, and WSL profile-smoke evidence
agree. It creates a disposable profile under the matching Windows temp root and
does not add a general <code>--no-sandbox</code> argument. Intentional overrides
can use <code>--browser-build</code> or <code>--browser-profile</code>.
Use <code>pnpm smoke:local-dashboard-runtime
-- --expect-marker "Stream port"</code> to verify the already installed service
without replacing the binary. If the dashboard detects a stale or missing
manifest, it renders a <code>Runtime contract drift</code> warning above the
control surface. <code>agent-browser install doctor --json</code> and
<code>agent-browser doctor remote-view --json</code> include the same
<code>dashboardRuntime</code> manifest, so CLI and dashboard readbacks describe
the same installed binary and embedded UI bundle.

Run <code>pnpm test:local-dashboard-publisher-lifecycle</code> after changing
standalone listener ownership, quiescence, restart, or rollback behavior. The
fixture uses isolated temporary processes and does not replace the installed
runtime or stop the live dashboard. Run <code>pnpm
test:local-dashboard-publisher-orchestration</code> after changing top-level
build, backup, replacement, handoff, readiness, or rollback ordering. That
fixture uses isolated real files and injected adapters without building,
installing, restarting, or attaching to a browser. Publication reports bind the
built, installed source, backup, replacement, and restored binaries to SHA-256
evidence. Backup mismatch fails before quiescence. Restore failure remains
secondary to the initiating publication error, and restart occurs only when the
current binary still matches a verified backup or verified replacement. Before
quiescence, a secured atomic transaction is written under
<code>~/.agent-browser/publications/</code>. The next invocation recovers an
incomplete verified replacement to readiness or a verified source to rolled
back before any new build. Exact handoff descriptors and already-resumed PID/CDP
evidence prevent duplicate resume; unknown installed bytes fail closed.
Run <code>pnpm status:local-dashboard-publication</code> for strictly read-only
journal, lock, phase, and artifact inspection. Run <code>pnpm
recover:local-dashboard-publication</code> only to reconcile an incomplete
transaction; it never falls through to a new build.
The installed Service dashboard reads the same evidence from authenticated
<code>GET /api/service/publications/local-dashboard</code> and shows a
Publication status light plus a review alert when a publisher is active,
verified recovery is available, or installed bytes are unknown. The surface is
read-only and has no recovery button or POST route. A recoverable transaction
shows <code>pnpm recover:local-dashboard-publication</code> as an explicit
operator command only after its phase and artifact evidence are visible.
The transaction status also states whether an exact retained-browser guard was
required and whether its final check passed, without exposing the session,
target, or URL in the public status projection.

Run <code>pnpm test:rust-isolated</code> for a local full Rust suite. It uses a
temporary home, agent state root, socket directory, and runtime directory and
forces serial execution so tests cannot share the operator's live browser
state. A focused Rust filter may be passed after <code>--</code>.

An available profile tile provides <strong>Open browser</strong>, which opens
the guided launcher with that exact profile selected and runs its no-launch
access-plan preflight. Every live service-owned browser provides
<strong>Close</strong> in the workspace tree and Service browser table.
Detected non-owned browsers retain screenshot, watch, and borrowed-input
controls without lifecycle ownership.

## WebSocket protocol

The dashboard connects to the same WebSocket endpoint used by [Streaming](/streaming), with additional message types for observability:

### Command events

Sent when a command begins executing:

```json
{
  "type": "command",
  "action": "click",
  "id": "r123",
  "params": { "selector": "@e5" },
  "timestamp": 1711367000000
}
```

### Result events

Sent when a command finishes:

```json
{
  "type": "result",
  "id": "r123",
  "action": "click",
  "success": true,
  "data": {},
  "duration_ms": 45,
  "timestamp": 1711367000045
}
```

### Console events

Sent when the browser logs to the console:

```json
{
  "type": "console",
  "level": "log",
  "text": "Page loaded",
  "args": [{"type": "string", "value": "Page loaded"}],
  "timestamp": 1711367000100
}
```

The `args` array contains the raw CDP `Runtime.consoleAPICalled` arguments for programmatic access. Object arguments include preview data (e.g. `{userId: "abc", count: 42}` instead of `"Object"`).

These are in addition to the existing `frame`, `status`, and `error` message types documented on the [Streaming](/streaming) page.

## Architecture

The dashboard is a Next.js static export (`output: 'export'`) that produces plain HTML, CSS, and JS. It lives at `packages/dashboard/` in the monorepo and is built with:

```bash
pnpm build:dashboard
```

The dashboard is embedded into the CLI binary at compile time using `rust-embed`. Plain HTTP requests serve the embedded dashboard assets, while WebSocket upgrade requests are handled as before.

## AI Chat

The dashboard includes an optional AI chat panel powered by the [Vercel AI Gateway](https://vercel.com/docs/ai-gateway). When enabled, a **Chat** tab appears in the right pane alongside Activity, Console, Network, Storage, and Extensions.

### Setup

The Chat tab is always visible. Set the API key to enable responses:

```bash
export AI_GATEWAY_API_KEY=gw_your_key_here
agent-browser dashboard start
```

Optionally override the gateway URL or model:

```bash
export AI_GATEWAY_URL=https://ai-gateway.vercel.sh   # this is the default
export AI_GATEWAY_MODEL=openai/gpt-4o-mini           # default: anthropic/claude-sonnet-4.6
```

### How it works

The Rust server proxies chat requests from the dashboard to the Vercel AI Gateway and streams responses back using the Vercel AI SDK's UI Message Stream protocol. The dashboard frontend uses `useChat` from `@ai-sdk/react` with `DefaultChatTransport`.
